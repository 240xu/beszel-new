# beszel-new

**beszel-new** 是 [Beszel](https://github.com/henrygd/beszel) 的一个 fork，为 **Panasonic CFQV8-1** 这台 NAS 增加上游没有的硬件采集与风扇控制能力：扩展硬件指标采集（CPU 频率与调频策略、NVMe 健康、WiFi、ACPI/DPTF 热区、风扇状态）、读取 pfanel 曲线历史，以及带完整护栏的风扇档位写入与温控曲线编辑。

它只适用于 Panasonic CFQV8-1。本项目不做通用化，也不承诺其他机型可用。

### ⚠️ 与上游同步：没有共同祖先，**不能**直接 rebase

这一条写在这里是因为「改了模块路径所以能 rebase」是一个很容易被默认成立的假设。它在这里**不成立**：

```console
$ git merge-base HEAD v0.21.0     # 无输出，退出码 1
```

原因是本仓库的历史**被重写过**。仓库里的 `v0.21.0` / `baseline-v0.21.0` 两个 tag 指向 `ec96c13`（上游的 release 0.21.0 提交，带 PGP 签名），而本仓库 HEAD 线的根提交是 `577694c`：

| | `ec96c13`（tag 指向） | `577694c`（HEAD 根提交） |
|---|---|---|
| tree | `dd4ac30` | `dd4ac30`（**完全相同**） |
| parent | `e597dd94…` | **无**（成了根提交） |
| gpgsig | 有 | **无** |

即 `577694c` 是上游 v0.21.0 的**内容等价副本**（单提交引入 575 个文件），但父提交被截断、PGP 签名被剥除。`ec96c13` 只作为 shallow 边界存在，**不属于任何分支**，所以 git 找不到共同祖先。

**后果**：把本仓库 rebase 到上游 `v0.21.0` 之上，重放的是**整棵树**而不是一小段增量差异 —— 这不是「rebase」，是把上游重新导入一遍。同步上游需要按文件比对人工搬运，细节与代价见 [DEVELOPMENT.md](./DEVELOPMENT.md)。

### ⚠️ 两个 baseline tag 是本地参考点，不是可用的对比基线

`v0.21.0` 与 `baseline-v0.21.0` 都指向 shallow 边界 `ec96c13`。凡是指向该边界的 ref，推送时会被远端拒绝：

```
! [remote rejected] v0.21.0 -> v0.21.0 (shallow update not allowed)
```

所以：**它们推不上去**，`git push --tags` 会因此退出 1。而分支能正常推送 —— 这组合最容易误判：命令报了错、退出码非零，但**仓库其实已经发布了一半**。（`git push --follow-tags` 退出 0，但只推得动分支。）

可以用它们做**本地树比对**（`git diff baseline-v0.21.0..HEAD -- go.mod go.sum` 这类），这是有效的；不能把它们当作「已发布的、可被别人检出的对比基线」。

⚠️ 另有一个操作陷阱：本仓库 `origin` 的 fetch refspec 被设成了 tag-only（只抓 `v0.21.0` 这一个 tag）。这意味着 `git fetch origin` **永远不会更新分支**，只更新那个推不上去的 tag。

## 硬件前提：仅 Panasonic CFQV8-1

以下前提全部来自**本机实测**，是这个项目能成立的前提，也是它的边界。**别的机器这套假设大概率不成立。**

⚠️ **样本量是 1。** 下面每一条都只在**一台** Panasonic CFQV8-1 上核对过 —— 没有第二台机器做过交叉验证。凡是依赖这台机器具体数值的结论（hwmon label 排布、ACPI 实例号、固件公布的档位集合），换机器都应视为**未验证**，而不是「大概也一样」。

- **风扇没有真实转速传感器。** 固件上报的 `fan_speed_rpm` 是哨兵值 `0xFFFFFFFF`，不是转速。本项目因此**不展示任何转速**：没有 tach 就没有转速的共识来源，任何数字都是编的。数据结构里的 `rpm_est` / `rpm_est_is_estimate` 字段**保留在 wire 上**（不破坏既有契约），但界面不消费它。
- **风扇阶梯表来自 ACPI `_FPS`，按「发布了什么」发现，不按设备名。** 读取路径不写死任何设备：先在 `INT340*` 里按**解析出来的实例号**排序（字典序会把 `:10` 排到 `:02` 前面），再取**唯一发布了数字 `state<N>` 表**的那一个目录。本机同时发布的 `INT3404:01` 是一个**只有 description/modalias、没有任何 state 文件的空壳**——它不是第二台风扇，把它当干扰项排除是靠内容判定，不是靠名字。
- **可写档位是「两处来源的交集」，不是一张写死的名单。**
  `白名单 = profile 声明的 static_duties ∩ 固件 _FPS 公布的档位`。两个来源**缺任一即全部拒绝**（报错分别是 `ErrDutySetUnknown` / `ErrPlatformUnknown`），这是有意的保守设计，理由见 [DEVELOPMENT.md](./DEVELOPMENT.md)。
  ⚠️ **`profile` 是一份部署前置条件**，装不上就会「风扇面板点不动 + 曲线保存被拒」，详见 DEVELOPMENT.md 的部署章节。
- **`0` 是「请求零占空比」，不是 auto。** 反汇编该机 ACPI 方法确认：`_FSL` 的实参一路写进 EC 风扇占空比寄存器，**全链没有对 0 的特判**，`_FPS`/`_FST` 也都不报告 EC 的曲线模式，所以**软件侧判不出写 0 会不会停转**。因此 `0` 不在白名单里，界面也不提供它。**不要把它当作「交还固件曲线」来用。**
- **EC 路径必须现场探测，不能照抄文档。** `THERMAL_ZONE` 是热区温度文件的**完整路径**，不是热区名字；`EC_ROOT` 与 `FAN_DEVICE` 是两个**互相独立**的配置键，谁也不能从谁推导出来。把这两点搞错的表现是：要么读不到，要么读到别人的数据。

## ⚠️ 安全警告：本项目会改变物理风扇转速

**这不是一个纯粹的只读监控工具。启用风扇写入能力后，你的每一次档位写入都会实际改变这台机器的物理散热行为。** 在你理解下面每一条之前，请不要开启它。

已实现的护栏：

- **写档位需要 admin 权限，并且必须显式 `confirm`。** 没有确认意图的请求会被拒绝。
- **`pfand` 守护进程运行时，手动档位会被拒绝。** 守护进程持有风扇控制权时，人为接管不会被放行——避免两套控制逻辑互相踩。
- **包温达到紧急边界时拒绝写入。** 紧急边界取自温控曲线自身的 `EMERG` 值，不是写死的常数。越热越不许手动降速。
- **曲线本身有一个来自本机的绝对上限，且拒绝兜底。** 曲线的温度上限从**这台机器**的 hwmon 读取（按传感器 label 选，不按索引），**读不到就拒绝保存，没有任何默认值**。所以一条在别的机器上合法的曲线，在这台上可能被拒 —— 这是有意的：宁可不许写，也不要用一个猜的上限。
- **写入失败有熔断与回滚。** 连续写入失败达到阈值即触发熔断；在熔断冷却期内控制路径只放行一次探测写入；已经写下去但未被守护进程接管的档位会被回滚，不会把风扇留在一个无人看管的状态。
- **手动档位是有时限的，但不会再自动「交还曲线」。** 到期时会触发一次交接尝试；然而如上所述，**没有任何占空比能被证明会把这台风扇交还给曲线**（写 `0` 是在请求零占空比，不是复位），所以这次尝试会**拒绝写入并把档位保持住**（`DeclineNoHandover`），转而提示人工处理。
  ⇒ **后果你要知道：设了手动档位之后，它会一直保持到你手动改掉为止。** 上面那条紧急边界护栏在每次写入尝试时仍然生效，所以这不是「无人看管」，但它确实是「没人替你改回来」。

即使有这些护栏，它们也是 AI 生成并由测试覆盖的，不是经过现场验证的安全关键件。请自行评估风险。

⚠️ **下面这六条护栏的验证状态，需要说清楚**：它们是**已实现的决策逻辑**，由单元与集成测试覆盖（测试用替身驱动整条拒绝/放行路径），但**从未在真实硬件上执行过一次写入**。也就是说，这些护栏证明的是「给定同样的输入，代码会做出同样的判断」，**不是**「在真实 EC 上写入过一次并成功回滚/拒绝」。

⇒ 这不是「已现场验证」与「未现场验证」的区别，而是**一个更靠前的区别**：验证只发生在替身上。首次在真机上启用写入前，请按「这条路径从未跑过」来对待。

## 开发

### 新 clone 从零跑通

⚠️ **干净检出的仓库上直接 `make test` 是红的**，而且会以看起来像环境问题的方式红。原因有两条，都是仓库自身的结构决定的。

**第一步：装前端依赖。门禁是 bun-only 的，没有 npm 回退。**

```bash
curl -fsSL https://bun.sh/install | bash
export PATH=$HOME/.bun/bin:$PATH     # 见下面的 PATH 陷阱
bun install --cwd internal/site
```

⚠️ **`bun` 默认不在非交互 shell 的 `PATH` 上** —— 它装在 `~/.bun/bin`。`ssh host 'make test'`、cron、CI runner 这类不经过登录 shell 的场景都拿不到它。这正是本项目曾经发生过的故障的成因：**当时 204 个前端测试从未运行，而构建仍然报告成功**（条数以 `make test` 的实跑输出为准）。门禁现在会因此**非零退出**而不是静默跳过，但你若在本地终端之外跑，务必自己先 `export PATH=$HOME/.bun/bin:$PATH`。

**第二步：处理 `internal/site/dist`。**

`internal/site/embed.go:9` 上有 `//go:embed all:dist`，而 `internal/site/dist` **在 `.gitignore` 里**，不进仓库。于是干净检出的树上 `dist` 目录不存在，Go 编译器找不到要嵌入的文件：

```console
$ go build -tags='testing no_ui' ./...
internal/site/embed.go:9:12: pattern all:dist: no matching files found
$ make test-go
... FAIL github.com/henrygd/beszel/internal/alerts [setup failed]   # 共 10 个包
```

要么真的把前端构建出来填上它，要么按 `Makefile` 里 `build-hub-dev` 一直在用的方式打一个桩：

```bash
# 真构建（推荐，产物与线上一致）
bun run --cwd internal/site build

# 或者打桩，让 Go 侧能编译即可
mkdir -p internal/site/dist && touch internal/site/dist/index.html
```

打桩之后 `make test-go` 即恢复全绿。

**第三步：跑门禁。**

```bash
make test
```

### 门禁的真实含义

`make test` 是 `test-go` + `test-site` 的**合取**，它自己不拥有任何跳过路径 —— 所以它只能在两套都绿时退出 0。

- **缺 `bun`** → 前端门禁拒绝运行，非零退出。
- **缺 `node_modules`** → 同上，非零退出。
- 两者都**不会**退化成「跳过但通过」。曾经有一个 `BESZEL_ALLOW_SITE_TESTS_NOT_RUN` 开关能把拒绝变回退出 0，它已被**删除**而不是收紧：一个报告成功却没有证据的旋钮本身就是缺陷。

前端门禁本身先跑它自己的自测（一条会随实现增减的契约，以实际输出为准），确认「拒绝路径」不是靠信仰成立的，然后才跑真正的套件。运行结束会打印实测的通过条数与登记失败条数 —— 以那行输出为准，不要引用文档里的旧数字。当前 `known-failures.txt` 是空的：登记失败集里一条也没有。

⚠️ **门禁不证明站点能构建。** CI 也是靠上面那个 `mkdir -p dist && touch index.html` 桩让 Go 侧编译过去的，所以**流水线从头到尾没有验证过前端能否真的 `build` 出来**。前端能不能构建是另一条独立的、目前未接入门禁的检查 —— 想验它就跑 `bun run --cwd internal/site build`，见下面。

### 前端命令

⚠️ **`bun test` 是错的命令，不要用它当门禁。** 裸 `bun test` 不加载 preload，碰到 `localStorage` 的用例会直接抛 `ReferenceError: localStorage is not defined`，若干文件整个加载失败，套件是红的。门禁显式传了 preload：

```bash
bun test --preload ./tests/bun-preload.ts   # 这才是门禁实际跑的东西
```

真正的门禁入口是 `make test`（或只跑前端那半的 `make test-site`）。前端另外两条：

```bash
bun run --cwd internal/site build   # lingui extract + lingui compile + tsc -b + vite build
```

> ⚠️ **`tsc -b` 单独跑不算门禁。** 它只做类型检查，不产出构建产物，也不执行 `lingui extract/compile`。**改动涉及 i18n、资源引用或打包配置时必须实际跑 `build`** —— 否则「类型过了」与「能构建」是两回事。

> ⚠️ **`build` 会改脏被 git 跟踪的 `.po` 文件** —— `lingui extract --overwrite` 会重写全部翻译源。构建完成后请还原：
> ```bash
> git checkout -- internal/site/src/locales
> ```
> 否则你会把一次纯构建产生的、几十个文件的无关翻译 diff 带进提交。
> ⚠️ 还原时**只还原重排**：`zh.po` 已提交过真实的 i18n 变更，直接 `git checkout` 整个 `locales` 目录会把它一起抹掉。逐个文件比对后再还原。

参与开发前请先读 **[DEVELOPMENT.md](./DEVELOPMENT.md)**。里面记录了这个项目真正吃过的亏（契约参数抄文档抄错 5 次、断言跟 import 的常量比导致断言失效 3 次、`?? 0` 静默兜底把「未上报」显示成 0% ），以及审计流程与核心纪律。**只读 README 就动手改，大概率会重蹈覆辙。**

## 验证状态

不把「读过代码」「测过逻辑」「在真机上成立」混成一句话。下面按证据强度分三档。

### 已实测（本机验证过，有可复现的观测）

- **`_FPS` 阶梯是发现的，不是写死的** —— 读取路径按解析出的 ACPI 实例号排序，取唯一发布了数字 `state<N>` 表的目录；`pluscheck` 在本机实读到 11 个编号档位（`state1..state11`，另有 `state0=0`）。⚠️ 这 11 是**这台机器固件的快照**，不是常量。
- **`INT3404:01` 是一个空壳** —— 只有 description/modalias、没有任何 state 文件。排除它靠「发布了什么」判定，不是靠名字。
- **DMI 三元组** —— `Panasonic Corporation` / `CFQV8-1` / `001`，profile 按全字段 AND 匹配。
- **hwmon 的 label 陷阱** —— 按索引取温度上限会取错：nvme 的 `Composite`（82.85°C）排在 coretemp 的 `Package id 0`（100°C）**前面**，两者 `temp1` 索引还相同。必须按 label 选。
- **ACPI `_FST` 的档位读法** —— 反汇编确认 `_FSL` 实参一路写进 EC 占空比寄存器，全链**无 0 特判**；`_FPS`/`_FST` 都不报告曲线模式。
- **`go build` 与 `go test` 全绿**，`make test` 退出 0（门禁自测 + 前端套件）。
- **前端门禁** —— 历史上出现过「套件只剩 2 条登记失败」的形态；这两条已被查清是**守卫钉住过期文案**（不是产品缺陷）并修复。现在的形态是**登记集为空**。套件条数随开发变动，以门禁输出的那行统计为准。

### 已实现，但从未在真实硬件上执行

## 已知限制

诚实列出，包括对我们不利的部分：

- **渲染层没有真渲染测试，源码护栏不能替代它。** 前端的 i18n 用 lingui 编译期宏（`t\`\``），而测试运行在 **Bun 的 runner** 上，它不会执行 SWC 的编译期插件（仓库里 `.swc/plugins/` 下确实有一个 lingui 插件二进制，但 `bun test` 不加载它）。因此部分组件的正确性只能由「源码结构断言」保证。
  ⚠️ **这类护栏只防结构漂移，不防运行时行为。** 任何声称「渲染层已测」的表述都不成立 —— 不要因为护栏是绿的就把渲染行为当成已验证。
- **档位候选列表仍是跨语言镜像。** 前端的 `FAN_DUTIES` 与后端白名单是两份独立维护的副本，靠防漂移测试保证一致。这是妥协：正确的解法是让后端暴露一个端点、前端从接口取 —— **该端点尚未实现**，见下方「计划中」。
- **降采样记录里扩展指标为空。** 120m / 480m 这些降采样周期的记录，其 plus 数据是空的 —— 上游的聚合器不会累加 plus 分段。这意味着**看长期趋势图时扩展指标会断档**，不是「没数据」，是聚合器根本没算。
- **任何 admin 账号都能停掉风扇守护进程。** 信任域在这里已经从「管理账号」扩大到了「控制物理散热」。这是一个真实的授权边界问题，当前没有更细的权限划分来兜底。
- **翻译只完成了一部分。** 扩展指标的界面文案没有提交过任何一条新翻译，中文界面下很可能看到英文原文。这是已知缺口，不是配置问题。
- **审计过程文档不随本仓库分发。** 任务计划、五组审计报告、修复报告、变异日志都保存在开发者的本地工作区里，该目录已被 `.gitignore` 排除，`git ls-files` 里一条也没有。**所以本文档引用的那些审计记录，你在 clone 下来的仓库里是读不到的。** 上面那些护栏为什么长成那样，只能从本文档与代码注释里读 —— 而这两处的诚实度，就是你能拿到的全部证据。

## 计划中（**尚未实现**，不要当成已有能力）

以下条目**只有决定，没有实现**。写在这里是为了让它们被看见，而不是为了让它们看起来已经可用。
